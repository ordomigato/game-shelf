# Threading a Postgres change all the way through

## Where things live

- `server/db/schema.ts`: Drizzle table definitions, the single source of
  truth for the schema.
- `server/db/migrations/`: SQL migrations generated by drizzle-kit.
  Committed, never edited by hand once applied anywhere.
- `server/utils/db.ts`: `useDb()`, the Drizzle client over Neon's HTTP
  driver. Auto-imported in server routes.
- `shared/types/collection.ts`: `FieldDefinition`, `ItemData` and friends,
  shared by the browser and the server.

## Structured columns vs JSONB

Fixed facts that every row has, that the app filters or joins on, or that
other tables point at, are real columns: owner, title, visibility,
timestamps, foreign keys. Only the **user-defined** part lives in JSONB:
`blueprints.fields` holds the field definitions, `library_items.data` the
values keyed by `FieldDefinition.id` (across every blueprint the item's
collections use). Don't push ordinary columns into JSONB to skip a
migration.

Postgres doesn't validate JSONB contents. Values are written through
`applyFieldValues` (`shared/utils/field-values.ts`), which accepts only the
fields of the collection's blueprint, checks each value against its type
(`select` must be one of `options`, rating 1 to 5, and so on), and leaves
values for other blueprints untouched.

## The collections model

- `games` and `platforms`: the shared catalog of IGDB games, keyed by IGDB
  id, the same for every user. Only the server writes them, from IGDB
  (`ensureCatalogGames` in `server/utils/catalog.ts`), never from a request
  body, and refreshes a game older than 30 days. No owner column, so no
  owner filter, and nothing a user sends changes them. See `igdb`.
- `library_items`: one row per game per user (a partial unique index on
  owner + `igdb_id`), however many collections it's in. An IGDB game links
  to the catalog by `igdb_id`, and its name and cover come from there
  (left join with `catalogJoin`, then `itemName` / `itemCoverId` or
  `toLibraryItem`). A game added by hand has no `igdb_id` and keeps its own
  `name`.
- Owned and the Wishlist are not collections. They are the `owned` and
  `wishlisted` flags on `library_items`, with `owned_on` and `wanted_on`
  (catalog platform ids, the versions). Check constraints make "both"
  impossible except across versions: a platform is never in both lists,
  a non-empty `owned_on` needs `owned` (likewise `wanted_on` and
  `wishlisted`), a game on both lists needs a non-empty `wanted_on`, and a
  game is on at least one list. `shared/utils/lists.ts` holds the same
  rules and the actions on them (`applyListAction`: got it, move to
  Wishlist, tick, untick, set the platforms), which
  `changeItemLists` in `server/utils/lists.ts` applies. A game left on
  neither list is deleted with its values and collection links.
  `getList` reads a list (owner only, 404 for anyone else) with the custom
  collections each game is in. A new game is owned unless it's added to
  the Wishlist, and adding a game to a custom collection never touches its
  flags. Custom collections hold owned and Wishlist games alike.
- `collection_items`: the junction table (composite primary key), with
  `position` and `added_at`. Custom collections only.
- `collections`: owner, `blueprint_id`, title, `slug` (unique per owner),
  visibility. All custom. `owned` and `wishlist` are reserved slugs, since
  the list pages live at `/u/<username>/shelf/owned` and `.../wishlist`.
  Only collections count toward the plan's collection limit. The Wishlist
  is capped at the per-collection game limit (`assertListRoom`), and Owned
  only by the library's.
- `blueprints`: shared (named) or private to one collection. A blueprint in
  use can't be deleted (`restrict`).

Every query on these tables is scoped to the owner from `requireAuth`.
Helpers live in `server/utils/collections.ts`. Use them rather than
querying in routes, and keep the owner filter in every new one.

## Order of work

1. **Schema** in `server/db/schema.ts`. Foreign keys get an explicit
   `onDelete`. Add an index for any column used to look rows up
   (`*_id` foreign keys especially).
2. **Generate the migration:** `npm run db:generate -- --name <what>`.
   Read the SQL it wrote. A rename can come out as drop-and-add, which
   loses data. Fix that before committing.
3. **Apply it to `dev`:** `npm run db:migrate` (runs through `sst shell`
   so it gets the dev `DatabaseUrl`).
4. **Server utils** in `server/utils/` for each operation. Routes call
   these and don't build queries inline.
5. **User scoping.** The user comes from the verified Cognito token, never
   from the request body or params. Every query on private data filters by
   owner, and every read of someone else's collection checks
   `visibility = 'public'`.
6. **Validate input** with `readValidatedBody` / `getValidatedQuery`
   before it reaches the database. Cap string lengths.
7. **The composable and UI** in `app/`. See `ui-conventions` and
   `plain-language`.

## Fixed sets of values are text with a check, not enums

Postgres can't use an enum value in the transaction that added it.
drizzle-kit runs all pending migrations in one transaction, and a release
often bundles many migrations, so a new enum value and the first thing
that uses it would land in the same transaction and fail. So a column with
a fixed set of values is `text` with a check constraint (like
`users.plan`: `plan in ('free', 'pro', 'max')`), narrowed in Drizzle with
`.$type<...>()`. Adding a value means changing the check in the same
migration that starts using it. Don't add new `pgEnum`s. `visibility` is
the one left, and it doesn't change.

## Correlated subqueries

Inside a `sql` template, Drizzle writes a column like `${blueprints.id}`
without its table name. In a subquery that can silently point at the
inner table instead of the outer one (`where blueprint_id = id` compares
a collection with itself), returning wrong counts with no error. Write
subqueries with an alias and spelled-out names instead:
`(select count(*)::int from collections as used where used.blueprint_id = blueprints.id)`.
Check a new subquery against the dev branch before trusting it, since e2e
tests stub the API and won't catch it.

## Neon specifics

- The HTTP driver has no interactive transactions. Group writes that must
  succeed together with `db.batch([...])`. If something truly needs a
  transaction with reads in the middle, raise it before switching drivers.
- A sleeping Neon compute wakes on the first query, adding about half a
  second. Don't add retries or keep-alive pings to hide that.
- Each stage has its own Neon branch. `dev` is disposable. It can be reset
  from production in the Neon console.

## Production migrations

`npx sst shell --stage production -- npx drizzle-kit migrate` changes the
live database. Ask before running it, every time. A migration that drops or
rewrites data needs the user to say so explicitly.
